# 미송신 원인 조사

**후속 상태:** 이 문서는 당시 실행과 판단의 기록이다. [최종 v1.1.0 범위](../../release-v1.1.0.md)에서는 PC 미송신을 STM32 릴리스 차단 조건으로 사용하지 않는다. 시한 경과 sleep은 [후속 수정·60초 검증](../host-pacing-fix-2026-11-23/README.md)에서 보완했다. 원시 결과와 당시 readiness JSON은 변경하지 않았다.

2026-11-23. 제품 코드·기존 시험기·판정 기준은 수정하지 않았다. 진단용 Python 래퍼와 타이머 대조 시험을 별도로 실행했다.

**확인한 메커니즘은 PC 실행 재개 지연 → 송신 시한 초과 → 시험기의 슬롯 건너뛰기다.** UART와 파일 기록을 제거한 대조 시험에서도 재현됐다. 기존 시험기에는 시한이 지난 뒤에도 `sleep(0)`을 호출해 대기를 추가하는 지점이 있다. 특정 앱이 지연을 만들었다거나 과거 미송신 5건 모두가 동일한 내부 경로였다고 단정하지 않는다.

## 1. 기존 60초 기록

[기존 시험](../release-completion-2026-11-23/README.md)의 3,000개 예정 입력 중 5개가 송신되지 않았다. 4개 구간의 PC write 간격은 43.426 / 57.880 / 53.096 / 52.778ms다. wire와 samples CSV가 일치했고 실제 송신한 입력은 모두 응답과 대응했다.

이 중 세 구간은 직전 입력의 응답이 각각 5.723 / 5.955 / 6.410ms 만에 PC에 이미 도착한 뒤 다음 송신이 늦어졌다. 나머지 구간에서는 송신 지연과 응답 read 지연이 함께 관측됐다. 이 기록에는 sleep·I/O 함수의 진입/복귀 시각이 없어, 과거 5건 각각의 내부 지연 지점까지 복원할 수 없다. [시각 대조](original-context.json).

## 2. 실보드 120초 진단

[diagnose.py](diagnose.py)는 기존 시험기를 그대로 불러오고 sleep, 시리얼 read/write/in_waiting, 파싱, 측정 생성, 기록 큐와 CSV 쓰기에 경과 시간·스레드 CPU 시간·프로세스 CPU 시간 관측을 덧붙인다. 2ms 이상 호출과 모든 write를 메모리에 모으고 종료 후 기록한다. `gc`도 관측했다. 평균 빈 관측 호출 비용은 약 1.496µs였으며, 관측 부하가 0이라고 가정하지 않는다.

- 120초 예정 6,000개 중 5,999개 송신·모두 대응, 미송신 1개.
- 보드 내부·전송·증거 통과, 요청 전체 부하는 미확정.
- 일반 펌웨어 복원과 STATUS 8개 카운터 0 확인.
- [결과](instrumented-120s/results.json), [구간별 원시 시간](instrumented-120s/host-stages.json), [wire/CSV·콘솔/JSON·판정 대조](instrumented-120s/audit.json).

미송신 구간은 센서 시각 16,320→16,360ms이며 write 사이 경과 시간은 46.949ms였다.

| 이 구간에서 관측한 호출 | 경과 시간 | 해당 스레드 CPU 시간 |
|---|---:|---:|
| 수신 대기 바이트 조회 `data.in_waiting` | 13.957ms | 약 0.080ms |
| 송신 시한 경과 후 `sleep(0)` | 8.911ms | 약 0.020ms |

`in_waiting`은 pyserial의 `ioctl` 호출을 포함한다. 이 경과 시간만으로 드라이버 대기와 OS 실행 재개 지연을 구분하지는 못한다. 두 긴 구간에서 프로세스 전체 CPU 시간도 각각 약 0.077 / 0.022ms였으므로, 긴 경과 시간을 그만큼의 Python 계산량으로 해석할 수 없다.

## 3. UART 없는 대조 시험

[timer_control.py](timer_control.py)는 같은 20ms 시한과 슬롯 건너뛰기 규칙만 유지한다. UART·보드·프레임 파싱·기록 작업 스레드 없이 `sleep`으로 기다리며, 결과 파일도 종료 후에만 쓴다.

**60초 동안 3,000개 슬롯 중 3개를 놓쳤다.** 미송신을 동반한 대기는 다음과 같다.

| 요청 대기 | 실제 호출 경과 | 스레드 CPU 시간 |
|---|---:|---:|
| 1ms | 44.908ms | 0.035ms |
| 1ms | 29.912ms | 0.026ms |
| 약 0.089ms | 28.034ms | 0.032ms |

즉 UART 드라이버·보드 처리·CSV 기록이 없어도 현재 호스트의 타이머 대기/실행 재개 지연만으로 같은 종류의 슬롯 누락이 발생했다. 이 대조 시험은 특정 앱을 원인으로 지목하거나 서로 다른 실행의 누락률을 비교하기 위한 시험은 아니다. [전체 기록](timer-control-60s.json), [사건별 분석](analysis.json).

Python도 `sleep`의 실제 정지 시간이 시스템의 다른 활동에 따라 요청보다 길어질 수 있으며 `sleep(0)`을 아무 동작도 하지 않는 것으로 취급해서는 안 된다고 설명한다. [Python 3.12 문서](https://docs.python.org/3.12/library/time.html#time.sleep). [CPython 3.12.14 구현](https://github.com/python/cpython/blob/v3.12.14/Modules/timemodule.c#L2054)은 Unix sleep 경로에서 시스템 대기 호출 동안 GIL을 해제한다.

## 4. 코드에서 지연이 미송신이 되는 경로

`fcc_app/tests/test_perf_monitor/board_check.py`:

- 259행: 반복을 시작할 때만 시한을 확인한다.
- 260–297행: 콘솔·UART 수신, 파싱, 기록 큐 처리를 수행한다. 이 중 시한이 지나갈 수 있다.
- 298행: 남은 시간이 0 이하라도 `sleep(0)`을 호출한다. 이번 진단에서 실제로 추가 대기가 관측됐다.
- 323–331행: `pump_until()`이 돌아온 뒤 늦어진 시간을 계산하고 20ms 단위 슬롯을 건너뛴다. 미송신 입력이 생기는 직접 경로다.

첫 수정 후보는 시한이 지났으면 추가 sleep 없이 송신 스케줄로 복귀하는 것이다. 이 변경도 양수 sleep에서의 실행 재개 지연을 없애지는 못하므로, 이것만으로 30분 미송신 0개를 보장할 수 없다. 송신과 수신·파싱을 분리하는 설계 역시 같은 PC의 비실시간 스케줄링 영향을 완전히 제거하지는 않는다. 필요하면 별도의 결정적인 입력원을 검토해야 한다.

이번 요청은 원인 조사이므로 수정 후보를 제품 코드에 적용하지 않았다. 소스 해시 137개가 기존 검증본과 일치한다. 원본 판정·과거 기록을 보존했고, 진단 실행을 릴리스 합격 증거로 승격하지 않았다. [입력·도구 해시](provenance.json).

## 재현

다른 송신기가 포트를 사용하지 않는지 확인한 뒤 저장소 루트에서 실행한다. 첫 명령은 PERF 플래시와 종료 시 일반 이미지 복원을 수행한다. 이미 존재하는 output 디렉터리는 재사용하지 않는다.

```sh
caffeinate -dimsu python docs/test-results/host-pacing-cause-2026-11-23/diagnose.py --output /private/tmp/radar-host-stages-new --duration 120
caffeinate -dimsu python docs/test-results/host-pacing-cause-2026-11-23/timer_control.py --output /private/tmp/radar-timer-control-new.json --duration 60
```

첫 스크립트의 workspace·도구·포트 경로는 이번 macOS 환경을 기록한 값이다. 다른 환경에서는 해당 인자를 맞춰야 한다. 관측 비용과 실행 시점의 호스트 상태 때문에 누락 횟수는 재현마다 달라질 수 있다.
