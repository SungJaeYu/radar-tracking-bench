# 호스트 입력 중단 판정 수정

후속 실보드 검증: [30분 관측 부하 통과·호스트 정지 처리 확인](../host-input-retest-2026-11-23/README.md). 요청50Hz 전체는 슬롯943개 누락으로 미확정이며 아래 기록은 당시 결과로 보존한다.

2026-11-23. 판정 버전: `2026-11-23-host-input-v3`.

**호스트 입력의 연속성이 깨진 시험은 STM32 실패 대신 미확정으로 종료한다.**
이미 관측한 CRC·큐·지연·자원·복원 실패는 계속 실패다. 이번에는 PC 시험기와
판정기만 수정했고 펌웨어, 송신 주기/타임스탬프 생성 방식, 합격 한계는 바꾸지 않았다.
새 실보드 시험을 수행한 결과가 아니라 회귀 테스트와 저장 기록의 재평가다.

## 실제 발생한 순서

PC의 `time.monotonic()` 송신 시각과 패킷 안의 센서 시각은 서로 다른 시간축이다.
시험기는 50 Hz 예정 슬롯 번호 × 20 ms를 센서 시각으로 넣고, 실제 UART write
직전의 PC 시각을 별도로 기록한다. 밀린 슬롯은 건너뛰지만, 슬롯을 선택한 뒤
실제 송신까지 호스트 실행이 지연될 가능성은 남는다.

| 순서 | PC write 기록의 간격 | 패킷 센서 시각 | 보드 응답 |
|---|---:|---:|---|
| 정상 입력 | — | 1,537,180 ms | UPDATED / CONFIRMED |
| 호스트 입력 공백 | 1,159.582 ms | 아직 새 입력 없음 | 입력 없는 RESET / EMPTY |
| 지연된 입력 | 위 공백 후 송신 | 1,537,200 ms | STARTED / TENTATIVE |
| 다음 입력 | 32.160 ms | 1,538,340 ms | 입력에 대응한 RESET / EMPTY |

첫 RESET은 1,000 ms 수신 무응답 timeout에 부합한다. 그 뒤 지연된 입력은 이전
센서 시각보다 20 ms만 증가한 값으로 추적을 다시 시작한다. 다음 패킷의 센서
시각은 여기서 **1,140 ms 증가**한다. 펌웨어는 예측 간격이 **1,000 ms를 초과하면**
트랙을 비우고 해당 입력에 RESET을 반환하도록 구현되어 있으므로 두 번째 RESET도
규격에 맞는다. 그 입력으로 즉시 추적을 다시 시작하지 않는 것도 기존 계약이다.

원래 시험기는 고정 표적의 모든 입력에 STARTED 또는 UPDATED만 나와야 한다고
가정했다. 실제 입력의 연속성이 깨진 뒤에도 이 가정을 적용하여 정상 RESET을
`Normal stationary measurement rejected`라는 `board_internal` 실패로 기록했다.
이 분류가 이번에 수정한 문제다.

사용자가 설명한 PC의 동시 작업 부하는 호스트 실행 지연과 부합한다. 다만 당시
스케줄러 추적이나 각 함수의 진입/복귀 시각은 저장하지 않았다. 따라서 특정 앱,
OS 스케줄링, Python 실행 구간 중 무엇이 정지를 유발했는지까지 확정할 수 없다.
확인된 것은 **PC write 기록의 공백, 센서 시각 점프, 그에 부합하는 보드 RESET**이다.
PC write 기록은 물리 UART 선로의 도착 시각도 아니다.

## 바뀐 처리

`board_check.py`는 실제 송신한 측정을 먼저 기록한 후, 연속 정상 입력을 전제로
보드 응답을 평가하기 전에 다음 두 조건을 확인한다.

1. 측정의 PC write 간격이 PERF 이미지의 `CONFIG_RADAR_MEASUREMENT_TIMEOUT_MS`
   이상이면 중단한다. 현재 값은 1,000 ms이며 실행할 이미지의 `.config`에서 읽는다.
2. 순방향 센서 시각 간격이 펌웨어의 1,000 ms 예측 한계를 초과하면 중단한다.
   uint32 wrap은 정상 처리하고, 중복/역행 시각을 허용하는 예외는 추가하지 않았다.

중단은 `host_input_interruption`에 이전/현재 센서 시각, write 시각, 두 간격,
적용한 한계와 이유를 남긴다. 이를 보드 실패 check로 만들지 않고 기록을 닫고
일반 이미지를 복원한다. `run_completed=false`이며 CLI는 성공 코드 0을 반환하지 않는다.
작은 호스트 지터나 한 슬롯 누락을 매번 중단하는 규칙은 추가하지 않았다. 그런 누락은
기존대로 요청 부하 판정에 남으며, 위 조건은 연속 추적 가정이 깨질 수 있는 경계다.

`perf_acceptance.py`는 이 중단을 미확정으로 처리한다. 이미 저장된 위반 항목은
계속 검사하므로 다음과 같은 결과가 된다.

| 관측 | 판정 |
|---|---|
| 호스트 입력 중단, 알려진 보드 위반 없음, 최종 평가 미완료 | 보드/요청 부하 미확정, `passed=false` |
| 같은 중단 + CRC·20 ms 초과·큐 거부·계측 유실·CPU/스택 기준 위반 | 해당 분류 실패, 전체 실패 |
| 같은 중단 + 정상 이미지 복원 실패 | 증거 분류 실패, 전체 실패 |
| 입력은 정상인데 설명되지 않는 RESET/거부 응답 | 기존 엄격한 응답 검사 유지 |
| 요청 슬롯 일부 누락만 있고 관측 부하 평가 완료 | 기존대로 관측 보드와 요청 부하를 분리 |

RESET을 무조건 허용하거나 중단된 30분 시험을 합격시키는 변경이 아니다. 지연
20 ms, 스케줄러 비유휴 80%, 앱 스택 여유 25%, CRC/큐 오류 0 기준과 RTT의 진단 전용
정책은 그대로다. 호스트가 실제로 제공하지 못한 연속 부하는 검증했다고 표시하지 않는다.

## 검증과 원본 보존

- 수정 전 새 회귀 중 11개가 실패하여 빠져 있던 처리를 확인했다.
- 관련 시험 **121개 통과**, 전체 Python **924개 + subtest 9개 통과**.
- 999/1,000 ms 호스트 간격, 1,000/1,001 ms 센서 간격, 설정된 timeout,
  최초 입력·uint32 wrap, 원시 기록의 두 불연속, 중단/복원 경로를 검증했다.
- 호스트 중단이 CRC·지연·큐·CPU·스택·계측 유실·복원 실패를 숨기지 않는 회귀도 통과했다.
- [재평가](reassessment.json)는 원본에서 입증한 RESET 오분류 한 건만 분리했다.
  현재 판정은 **failed → inconclusive**이며 `passed=false`는 유지한다.
- 원본 `results.json`은 바이트 단위로 보존했고 SHA-256을 재평가에 기록했다.
  실제 보드 재시험이나 새로운 30분 결과로 취급하지 않는다. 새 guard는 더 일찍
  중단했을 것이지만, 재평가에서 그 가상의 기록이나 수신하지 않은 응답을 만들지 않았다.
