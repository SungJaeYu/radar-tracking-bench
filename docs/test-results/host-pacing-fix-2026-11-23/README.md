# 송신 시한 경과 sleep 수정과 최종 검증

2026-11-23. [v1.1.0 최종 범위](../../release-v1.1.0.md). PC 미송신은 STM32 합격·릴리스 차단 조건이 아니며 실제 제공한 부하에 함께 기록한다.

## 수정

`fcc_app/tests/test_perf_monitor/board_check.py`의 `pump_until()`은 수신/파싱이 이미 시한에 도달했어도 `sleep(0)`을 호출했다. 남은 시간이0 이하이면 추가 sleep 없이 복귀하도록 수정했다. `tests/firmware/test_perf_monitor.py`는 실제 nested pump를 모사 I/O·시계에 연결해 시한 도달/초과 및 남은0.5ms/1ms 대기를 검증한다. 수정 전2개 실패·2개 통과, 수정 후4개 통과다. 실제 OS 주기 보장을 주장하는 시험은 아니다.

## 미송신의 정확한 의미

FIFO는 순서를 정하고 pacing은 송신 시점을 정한다. 현재 시험기는20ms 예정 시각을 기준으로 지연되면 `floor((now-next_send)/0.02)`개 슬롯을 생략한다. 따라서 **PC 실행 지연 → 송신 시한 경과 → 해당 측정 생성·write 생략**으로 이어진다. 보드에 보냈다가 사라진 입력이 아니다. 실제 보낸2,993개는 모두 대응한다.

최종 실행의 센서 timestamp와 PC write 직전 시각을 대조한 결과:

| 직전→다음 센서 시각(ms) | 미송신 센서 시각(ms) | 개수 | PC write 간격(ms) |
|---|---|---:|---:|
| 1360→1420 | 1380, 1400 | 2 | 51.092875 |
| 11880→11920 | 11900 | 1 | 35.149833 |
| 18760→18820 | 18780, 18800 | 2 | 133.479958 |
| 18820→18880 | 18840, 18860 | 2 | 0.171000 |
| 19140→19200 | 19160, 19180 | 2 | 66.668958 |
| 26540→26580 | 26560 | 1 | 41.969625 |

18,820ms 입력의 실제 write 시각은 첫 입력 write 기준 약18,894.789ms다. 다음18,880ms 입력은18,894.960ms에 기록됐다.0.171ms 행은 새 긴 정지가 아니라 앞선 지연 이후 다음 반복에서 뒤처진 슬롯을 추가 생략한 것이다. 슬롯 계산과 write 사이에도 지연될 수 있으므로 짧은 연속 송신 간격을 완전히 방지하는 구현은 아니다. 이 기록은 UART 선로 도착 시각이 아니다.

[사건별 수치·입력 해시](missed-slots.json). 최신 실행에는 함수별 호출 시간 계측을 넣지 않아10개 각각을 sleep/ioctl에 귀속할 수 없다.

별도 [수정 전 원인 조사](../host-pacing-cause-2026-11-23/README.md)의120초 실행에서는 미송신 구간에 `in_waiting`13.957ms와 시한 경과 `sleep(0)`8.911ms가 겹쳤다. UART 없는 대조 시험에서도 요청1ms sleep이44.908ms 후 반환하며 슬롯 생략이 재현됐다. 특정 앱은 지목하지 못한다.

## 후속 개선

[v1.1.1 #8](https://github.com/SungJaeYu/radar-tracking-bench/issues/8)에서 입력 생략 없는 주기 재생, FIFO 처리, 송신 주기 설정과 지연 처리 정책을 검토한다. 무주기 FIFO는 처리량 부하 시험,40/100ms 간격은25/10Hz 시험이며50Hz 검증과 구분한다.50Hz는 현재 프로젝트의 부하 목표이며 STM32 하드웨어 스펙의 유일한 동작 주기가 아니다.

추적 예측의 dt는 프레임의 센서 timestamp 차이를 사용하고, 무수신 timeout은 보드 uptime으로 판단한다. 입력 순서·센서 시간·실제 전달 간격을 각각 기록해야 한다. 현재 릴리스에서 송신 구조를 추가 변경하지 않는다.
