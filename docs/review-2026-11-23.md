# 2026-11-23 종합 검토 및 수정 내역

**최종 상태:** [v1.1.0 완료 기록](release-v1.1.0.md)을 따른다. 아래는 기준 커밋 `20f069f` 이후 중간 검토의 수치와 변경 이력이다. 후속30분 관측 부하 통과 및 최종60초 검증을 완료했으며 PC 미송신·RTT는 릴리스 차단 조건이 아니다.

## 1. 최종 판정의 의미

| 항목 | 합격 기준/용도 | 새60초 실보드 |
|---|---|---|
| `board_internal` | 관측 부하의 보드 지연≤20ms, 큐·계측 오류0, CPU 구간 비유휴≤80%, 앱 스택 최소 여유≥25% | 통과 |
| `delivery` | 유효 입력/응답·순번·STATUS·송수신 개수의 무결성 | 통과 |
| `evidence` | 필수 관측·기록·요약·정상 이미지 복원 | 통과 |
| `board_qualification`, `passed` | 위3개 분류의 관측 부하 판정. CLI exit0도 같은 의미 | 통과, `passed=true`, exit0 |
| `requested_profile_qualification`, `requested_profile_passed` | 위 판정 + 요청 기간 전체·50Hz 예정 슬롯 누락0 | 미확정, false: 예정3,000개 중22개 누락 |
| `host_rtt` | 호스트 경로 진단. p99≤20ms/최대≤100ms 한도는 유지하지만 STM32 합격 조건에서는 제외 | p99 9.362ms, 최대117.529ms 진단 초과 |
| `full_coverage` | 소프트웨어 계측 밖 물리 경계·WCET 등까지 증명했는지 | false |

정해진 부하를 제공하지 못한 것은 그 부하의 검증 미완료이며 STM32 처리 실패와 다르다. 반대로 RTT를 제외했다고 입력 누락·CRC·큐 오류·불완전한 기록을 통과시키지 않는다. 과거 파일의 `passed=false`는 당시 정책의 원본으로 보존한다. 결과 소비자는 `acceptance_revision`과 `passed_scope`를 읽어야 한다.

## 3. 실보드 실패 원인 분석

원시8개 세션을 저장된 프레임 파서와 별도로 `binascii.crc_hqx`를 사용해 재파싱했다. TX/RX CRC·길이·불필요 바이트·미완성 프레임 오류0이며 CSV와 일치했다. 이것은 **PC가 기록한 바이트** 검증이며 실제 수신선 신호의 증명은 아니다.

### 과거 CRC 2건 — 조치 후 비재현, 해결 추정·원인 미확정

확장 계측의 장시간 시도와 짧은 재시도에서 보드 STATUS가 CRC1을 보고했다. 보드 수신 파서가 CRC 불일치를 집계한 사실이다. 이것만으로 STM32 하드웨어 결함이나 특정 코드 원인을 확정할 수 없다. 당시 실패 기록은 보존한다.

- 마지막 정상 STATUS→오류 STATUS 구간의 최대 PC 송신 간격은 각각21.057ms,26.768ms였다. 큰 호스트 정지가 CRC를 만들었다고 할 증거는 없다.
- 미응답 입력 시각158640/158660ms 뒤에는17개,18440ms 뒤에는28개 후속 입력 응답이 있었다. 단순히 중단 직전 전송 중이었던 표본이라고만 설명하기 어렵다.
- 두 번 모두 첫 누락 입력 index가 마지막 PERF 요약의 누적 측정 수(7837,902)와 일치했다. 요약/계측 경로를 의심할 단서지만 인과관계 증명은 아니다.
- 이후 ISR 집계·IRQ 차단 중 통계 처리 제거 후300초, 이번60초에서는 CRC0이다. 계측 설계 결함은 수정했지만 과거 CRC 원인 해결/장시간 무오류를 확정하지 않는다.
- 하드웨어 ORE/FE/NE 상태와 실제 RX 바이트/선로 시각이 보존되지 않았으므로 물리 링크와 보드 내부 유실을 더 좁히는 데 한계가 있다.

**현재 분류와 추정 원인**

| 분류 | 판단 | 근거와 한계 |
|---|---|---|
| 우선 가설: 이전 PERF 계측 코드의 수신 방해 | ISR 집계 및 IRQ 차단 중 통계 갱신·snapshot 복사가 UART 서비스 지연이나 바이트 유실에 기여했을 가능성 | 계측 구간과 누락 시점의 연관 단서가 있고, 해당 구조를 제거한 후300초·30분·최종60초 시험에서 CRC가 재현되지 않았다. 당시 ORE 등과 실제 수신 바이트가 없어 인과관계는 확정하지 못한다. |
| 대안 가설: 물리 링크의 일시적 신호 오류 | 배선·접촉·접지·외부 잡음 가능성 | 당시 선로 파형/FE/NE 기록이 없다. 근처 휴대전화가 원인이라는 근거는 없다. |
| PC `sleep(0)` | 별도로 확인하고 수정한 시험기 결함 | 송신 지연·슬롯 생략 경로이며 과거 CRC 2건의 원인으로 연결할 증거는 없다. |

CRC의 상태는 **조치 후 비재현으로 해결된 것으로 추정하되 원인은 미확정인 이력**이다. 현재도 재현되는 미수정 결함으로 표기하지 않고, 원인까지 입증된 해결로도 표기하지 않는다. 이후 같은 현상이 재발하면 이 기록과 비교한다. 별도 CRC 이슈는 두지 않는다.

### RTT 초과 — 유효한 호스트 진단, STM32 실패 판정에는 부적합

최초30분 최대 RTT220.246ms는 다음 송신 간격219.419ms와, IRQ 보완300초 최대 RTT328.516ms는327.317ms 공백과 겹쳤다.100ms 초과 RTT 중100ms 초과 송신 공백과 겹친 것은 각각11/21건,13/15건이다. 계측 실행에서는 요청한1ms sleep이75ms 동안 반환하지 않았고 그동안 스레드 CPU는0.025ms만 사용한 사례도 있다. 호스트 실행 지연의 증거지만 모든 RTT 꼬리의 원인을 하나로 특정하지는 못한다.

### 시험/판정 자체의 오류

초기 CRC 중단은 실패한 분류 검사를 저장하지 않아 전송 미확정으로만 표시됐다. 이후 실행은 중단 전 마지막 주기 요약을 최종 송신 개수와 비교하여 가짜 개수 불일치를 만들었다. 이 두 경로는 앞선 수정으로 보완됐고 회귀를 확인했다. 이번에는 정상 저장도 미완료로 표시하는 문제를 추가 수정했다. 과거 원시 결과는 덮어쓰지 않았다.

근거: [분석 스크립트](test-results/review-2026-11-23/analyze_failures.py), [구간별 수치·raw 재생 결과](test-results/review-2026-11-23/failure-analysis.json).

## 4. 검토 범위와 검증

펌웨어 UART RX/TX·parser→handler→TRACK·필터·PERF collector/reporter/resources, PC 운동/구간 시나리오·GUI·비동기 기록, 판정 코드와 문서를 검토했다. ISR SPSC 게시/소비 순서·단일 wrap·mutex 사용·Zephyr CPU 통계 매핑에서 추가 고신뢰 회귀 버그는 발견하지 못했다. 이는 모든 결함 부재나 WCET 보증이 아니다.

- **이번 실행:** Python904 passed +9 subtests. 최종 snapshot 저장 추가 후 관련24개를 재실행해 통과. 새60초 실보드 유효 측정2,981개 모두 대응, TRACK2,986개, STATUS61개, wire45,120바이트·요약14개. CRC·길이·큐·링·stale·계측 오류0. 원시 wire/CSV·console/JSON·판정 재생 일치. 정상 펌웨어 복원·STATUS0.
- **동일 펌웨어 작업본의 직전 검증:** CTest204개 등록 항목/224회 내부 실행, firmware5구성 통과.300초 PERF 관측 부하의 보드 판정 통과, 포화·복구95검사 통과. 이번 검토에서 펌웨어 소스 해시가 변하지 않았음을 대조했다. 이를 이번에 재빌드/재실행한 것으로 주장하지 않는다.
- **의도적으로 미검증으로 남긴 것:** 최신 확장 계측의30분 연속 시험, 누락 없는50Hz 입력, 물리 RX→ISR 및 마지막 TX stop bit, 정확한 IRQ 차단 시간/WCET, 전체 시스템 스택·모든 하드웨어 장애 조건. [전체 범위](stm32-performance-coverage.md).
